# Live parity for 14.35 on an arashouse lease: the first 14.35 server

Arashouse map ticket 46 ("prove the guard"). `arashouse run --lease <id> -- npm run parity -- --engine 14.35 --include-slow` ran the oracle (the vendored `Libs.dll` 14.35.0.43890 through the Windows host) and the port on the same inputs against a fresh lease of flavor `35`, case by case, on 2026-10-28. The lease was slot `35-01`: Aras Innovator Release 35, server `14.35.0.43890`, `http://172.19.0.1/ah-35-01` from WSL (`http://localhost/ah-35-01` from the oracle's Windows side), database `arashouse_35_01`, user `root`, with the password `arashouse get` made for the lease. The guard of ticket 45 (`oracle/src/live-targets.ts`) accepted it through `arashouse status --json`; nothing else changed. The command, the catalogue and the comparison (EXP-558 for the parallel exports) are those of the dev records, [`live-parity-14.35-export.md`](live-parity-14.35-export.md) and [`live-parity-14.35.md`](live-parity-14.35.md). The other engines' lease runs are [`live-parity-12.0-on-leases.md`](live-parity-12.0-on-leases.md) and [`live-parity-14.0.7-on-leases.md`](live-parity-14.0.7-on-leases.md).

The 14.35 dev records ran against the 12.0 SP9 dev instance, because no 14.35 server existed. This is the engine's first run against the server it was built for.

Per the round 5 correction, **equal cases do not prove the engines the same.** They show that these inputs reach no difference.

## What the 14.35 server showed

- **No new difference.** No case differed in the requests, the files, the log, the messages or the return code. The login, the version probe (`14.35.0.43890`, written `14.35.0.43890` by WIRE-022's formula for servers from 14) and the gate are equal in every case. No fixture, fix or `spec/bugs.md` entry comes from this run.
- **LP-040's false branch was not reached.** The ticket expected the false branch of LP-040 (`NeedToHandleNullPropertyValues`) to meet a 14.35 server here for the first time. On this server the test is false, so the preprocessor sends no LP-041 request and the import sends the generated `Property` items as they are (LP-042). But only a language-pack import makes such items (a `Property` row file, `context_action="lpimport"`), and the eight language-pack cases were skipped: the lease has no Languages `de` and `fr`, like dev, and the script never adds one. No case that ran sends a `Property` with that attribute, so the branch changes nothing the run compares. It stays pinned offline (`06-null-values.out`, `src/language-pack/` tests).

## Every difference from the dev record, explained

The port and the DLL agreed on every case, as on dev. What differs from the dev record is the server, and one thing that varies from run to run:

- **A Release 35 database is not dev's.** The read-only check of the lease (each export case's items, by type and id, from `fixtures/14.35/export/*/run.json`) found the same absences as on the `23` lease: the three cases in dev's own packages, `e38-variable-empty-value` and `e52-float-item-property` (`com.steepgraph.powerplay`) and `p4-folder-mapping` (`com.steepgraph.pagex`), which exported on dev and end with a `CItemException` on both sides here; and the Enterprise Search items of `e33-user`, `e36-variable-both-empty`, `e43-xclassificationtree`, `e44-xpropertydefinition` and `p1-order-six-forward`/`-reverse`, which still end `exported`. It also found the core List `Categories` (`EAB29654E2CD4D30B376957788198B40`) absent, by id and by name: the parallel-export cases `x-par-*`, `x-cancel-after-5-*`, `x-abort-*` and `x-template-shared-across-packages` export it with other Lists. They end as on dev, on both sides. These are the only three cases whose end differs from dev's; the other cases' `Nope` Lists are absent on dev too, on purpose.
- **Requests per case.** Compared with ticket 76's last dev runs case by case, 67 export, scratch-export, DB patch and console-mode steps sent the same number of requests, 31 more and 29 fewer. The read-only export cases follow the server's metadata, which differs between 12.0 SP9 and Release 35, as for 14.0.7 on `23`. A difference of one request in a parallel export, such as `p5-ref-on` (25 to 24), `mode-from-manifest-unknown-package` (25 to 26) or `mode-use-import-scratch` (33 to 32), also happens between two runs on the same server: two workers that miss a cache together send the same lookup twice (`live-parity-14.35-export.md`; EXP-558 compares those requests as a set).
- **Imports.** Every import step sent as many requests as on dev except step 1 of `s2-ref-both` and `s2-ref-only` and step 2 of `s2-ref-dep-present`, 2 fewer each (4 692 against 4 698). Their package references the stock List `Report Format Types` (`STOCK_LIST`, `oracle/src/import-packages.ts`). On dev the engine finds it and then reads and adds its `PackageReferencedElement`, 2 requests (`fixtures/14.35/import/s2-ref-only/step-1/transcript.jsonl`, requests 14 to 16); for a List the server does not have (request 13 there) it sends neither. Release 35 has no such List, by id or by name (read on a second `35` lease, which also reran `s2-ref-only` and `s2-ref-both` with their folders kept: equal, 29 and 49 requests).
- **The DB patch was refused by the slot's licence.** `dbpatch-apply` step 1 sent 15 requests against dev's 16. The rerun on the second lease kept its folders: the server answered `ApplyUpdate` with the fault `SOAP-ENV:Server.FeatureHasNoLicensesException`, `You do not have a valid license required to use feature Aras.ApplyUpdate.` So the engine wrote its `error` message, added no `DatabaseUpgradePatch` (the request dev sends after a good `ApplyUpdate`) and set the row's `upgrade_status` to `2`, not `1` (DBP-050, and the after-run edit that `spec/db-patches.md` describes). The port did the same, request for request, so the case is equal. On dev the second step meets this failure path through the server's "already applied" fault; here both steps do. So on this lease the DB patch shows the refusal path, not a patch applied: the slot is licensed with the 14.0 key that arashouse uses for flavors `23` and `35`, which does not cover `Aras.ApplyUpdate` on a Release 35 server. That is the slot's licence, not the library; it is noted for arashouse. `dbpatch-non-root` (the engine refuses the login before the server is asked) sent as many requests as on dev. The script's note for step 1 ("the oracle ended as applied, not as the recorded case says (applied)") comes from the outcome check seeing the `error` message the recorded run did not have, and printing only the end kind; it changes nothing compared.
- **`--all-packages`** exported every package of the lease, 10 667 requests a side against dev's 10 464 (Release 35's own packages); its output tree is byte for byte equal between the two sides.

## Not run

- **The 23 language cases** (5 import cases with language selection, 8 language-pack cases, 10 `lang-ml` export cases), skipped with the script's reason, as on dev. On a lease adding the Languages would harm nothing, since the database is discarded at return, but the script's rule and `AGENTS.md` still treat a Language as a change to refuse. Whether leases may lift that, which is also what would reach LP-040's false branch live, is for the amendment of `AGENTS.md` "Live Aras" (arashouse map ticket 47) or a ticket after it.

## What the lease held

Before the run, a read-only count on the fresh lease found no PackageDefinition, DatabaseUpgrade, ItemType, RelationshipType, Method, Form, Identity, Variable, SQL, List, Property or Field named `LIBSJS*`, and the script's own check passed. The import family's two sides created 2 377 scratch items and their cleanups deleted 2 367, each only after reading back the owner's name; nothing was kept or left unverified. The ten are the same ten as on dev and on the other leases (`live-parity-12.0-on-leases.md`). The DB patch cases made two items, the `DatabaseUpgrade` row of each side (the refused `ApplyUpdate` made no "Applied Updates" item and no link), and the oracle's DB patch cleanup deleted both. The same count after the run, before the lease was returned, again found no `LIBSJS*` item of any of those types.
