# Browser host: decision record

Settled on 2026-11-02 by a scout who read `src/` at 76ace6e4, with the captain's answers of the same day. The map this record belongs to has 34 tickets (33 tasks and one POC); the ticket tracker lives outside the repo, on Firstmate's side, and tickets are cited here by number. The rules that follow from these decisions are in [`spec/browser-host.md`](../spec/browser-host.md) (`HOST-200` to `HOST-299`).

## Destination

`import-export-libs-js` runs export, import, language-pack import and DB-patch application in a browser (Chromium, Firefox, WebKit), for all three engines (12.0, 14.0.7, 14.35), with output byte-identical to the Node build on the same inputs. Two proofs: the recorded fixtures replayed inside real browsers, and live parity against arashouse leases. The Node library and CLI keep working exactly as today: every existing test stays green with its assertions untouched, and the parity fixtures stay byte-identical. The CLI, `oracle/`, `tools/` and the test tooling stay Node-only.

## What the code says (evidence)

- The closure of `src/index.ts` is 132 source files. Eleven of them import a Node built-in: `client/digest.ts` (`node:crypto`), `client/transport.ts` (`node:http`, `node:https`), `client/timezone.ts` (`node:child_process`), `io/host-path.ts` and `io/windows-fs.ts` (`node:fs`, `node:path`), `io/temp-path.ts` (`node:crypto`, `node:os`), `import/package-files.ts` (`node:fs`, `node:path`), `import/import-helper.ts` (`node:os`), `export/run-log.ts` (`node:fs`, `node:path`), `export/import-export-manager.ts` (`node:os`), `db-patches/apply.ts` (`node:crypto`). Three more use `process` without importing it (`import/import-run.ts`, `export/output-folder.ts`, `export/manifest-selection.ts`), so 14 files touch Node directly. `@xmldom/xmldom` and `xpath` are browser-safe, and the XSL is re-implemented in TypeScript, so there is no native XML dependency.
- Ambient Node globals in core code: `process.cwd()` and `process.platform` as the defaults of `PathEnvironment`, `process.hrtime.bigint()` (`import/import-run.ts`), `process.env.USERDOMAIN` (`import/import-helper.ts`), `setImmediate` (`export/output-folder.ts`), and `Buffer` in 12 files.
- The environment is already threaded: `PathEnvironment {platform, cwd, normalizePaths}` is passed from `ImportExportManager` to the manifest, the output folder, `RunLog`, the loader and the DB-patch host. The seam is an extension of an existing parameter, not a new plumbing job.
- Every file call is synchronous (`statSync`, `readdirSync`, `writeFileSync`, `openSync` with `writeSync` for the log) and sits in synchronous chains. The File System Access API is asynchronous only, so no browser file API can be called from those chains. This decides D1.
- `PasswordDigest` is constructed and switched synchronously; Web Crypto's `digest()` is async and has no MD5 (D4).
- The wire layer takes an injected `HttpTransport` already, and `FakeTransport` exists, so a fetch transport is one more implementation.

## Design decisions

- **D1. A synchronous host file system, backed by memory in the browser; async loading and saving happen at the edges.** The engine's file calls are sync and reproducing NTFS semantics on top of them (`io/windows-fs.ts`) is the product. Making the layer async would touch about 40 call sites across export, import, language-pack and DB-patch paths and risks reordering effects the fixtures pin. Instead, `HostFs` is a sync interface with errno-coded errors (so `translateFileError` keeps working), the Node implementation delegates to `node:fs`, and the browser implementation is an in-memory POSIX tree (`MemoryVfs`). Packages are *mounted* into the tree before a run (zip, folder picker, File System Access, drag-drop) and the output tree is *committed* after it (zip download, directory write). Consequence: a package must fit in memory (Q5). OPFS sync access handles in a Worker were considered and rejected: they are sync for file bytes but directory listing is async, and they only cover OPFS, not user folders.
- **D2. The seam rides on `PathEnvironment`.** Add optional `fs: HostFs` and `host: HostEnv` to it. Every function that takes an environment uses `environment.fs ?? defaultHost().fs`. `defaultHost()` lives in one module, `src/host/default-host.ts`, that imports the Node implementation; the browser bundle and the Vite browser-test config replace that one module with `default-host.browser.ts` by alias. This keeps every existing test running unchanged under Node with no setup file and no global registration, and gives a hard guarantee: the browser graph cannot contain `node:*` because only that module reaches it, and a bundle-graph test fails the build if one slips in.
- **D3. One portable `path` implementation for both targets** (`src/io/path.ts`: the `posix` and `win32` subsets the code uses, `resolve`, `join`, `dirname`, `normalize`, `parse`, `isAbsolute`, `relative`, `basename`), differential-tested against `node:path` over a generated corpus. `win32` is needed on every host, because `getFullPath` runs the Windows rules everywhere (`io/host-path.ts`) and `path-browserify` has no `win32`. Using one implementation in Node as well removes a second code path.
- **D4. Pure-JS MD5 and SHA-256, synchronous, for both targets**, tested against `node:crypto` (`client/digest.ts`). Reason: the API is sync (above); Web Crypto plus a small MD5 would need SHA-256 async and ripple through `PasswordDigest`, `connection.ts` and `oauth.ts`. `node:crypto` stays only in the CLI's `membership-server.ts`. Random bytes and UUIDs come from the host (`crypto.getRandomValues`, which works in non-secure contexts, with `randomUUID` as an optimisation).
- **D5. `Buffer` stays in the source; the browser bundle gets the `buffer` package (feross) injected.** The product is byte-exactness (UTF-8 BOMs, latin1, UTF-16 with `swap16`, lone-surrogate handling), and replacing about 40 call sites with `Uint8Array` helpers would also force edits to existing tests that call `.toString("hex")` on returned buffers. A differential conformance suite over every Buffer method the core uses proves the shim equal to Node's, including lone surrogates and astral characters. Cost about 28 kB in the bundle. Rejected: rewriting to `Uint8Array`.
  - *Outcome (ticket 14, HOST-262).* The conformance suite (`src/browser/buffer-shim.test.ts`, 163 triples) found the package equal to Node's `Buffer` for every call the core makes, except in UTF-8: encoding a string that ends in two or more unpaired high surrogates drops the last one, and decoding a truncated or invalid multi-byte sequence gives more U+FFFD than Node's WHATWG decoder. The core's UTF-8 encode and decode sites (14 of about 40) now call `utf8Bytes` and `utf8Text` (`src/io/utf8.ts`, `TextEncoder`/`TextDecoder`), proved equal to Node's `Buffer` by the same suite, and a guard (`tools/buffer-usage.test.ts`) fails on a direct UTF-8 `Buffer` call or any call the suite does not compare. The rest of `Buffer` stays, as decided. `alloc(NaN)` also differs (the package returns an empty buffer, Node throws) and is not compared: the only caller passes `s.length * 2`.
- **D6. Entry points.** New `src/core.ts` (everything portable), `src/index.ts` = core + Node extras (`nodeTransport`, `localWindowsTimeZoneId` with `tzutil`, file helpers), `src/browser.ts` = core + browser extras. `package.json` `exports`: `"."` gains a `browser` condition and `"./browser"` is explicit, both with types; `sideEffects: false`. tsup gets a second config (platform `browser`, esm, es2022, alias for `default-host`, `inject` of the Buffer shim, metafile guard). The Node bundle's public API stays the same. As built (ticket 21, HOST-260, HOST-261): the Node extras turned out to be `nodeTransport` alone, because `localWindowsTimeZoneId` and the file helpers were made portable by tickets 08 and 06, and `nodeFs` and `nodeHost` are the default host, which the Node entry never exported, so the Node entry's runtime names are the 198 it had before. esbuild's `alias` maps packages and not files, so the replacement of `default-host.ts` is an esbuild plugin (`tools/browser-bundle.ts`), shared by the build and by the guard test. The second tsup config is a second file, `tsup.browser.config.ts`, run after the first by `npm run build`: tsup runs the entries of one config file in parallel and each one's `clean` would race the other's output, so `tsup.config.ts` stays as it was and owns `clean`. `@xmldom/xmldom` and `xpath` are inlined with the `buffer` shim (a one-file bundle that imports nothing); the licences of the five bundled packages are the banner of `dist/browser.js`. The bundle is 1.09 MB unminified (about 0.25 MB gzipped), the guard's budget is that plus 20 %, and minifying is left to the consumer's bundler.
- **D7. Typecheck ratchet.** `tsconfig.browser.json` (`lib: ES2022 + DOM + WebWorker`, `types: []`, so `process`, `NodeJS.*` and `node:*` fail) over the closure of `src/browser.ts`. It starts as an explicit `files` list of the 79 already-clean files of the closure (measured with an esbuild metafile) and grows to the single entry `src/browser.ts` as the seam tickets land. `npm run typecheck` runs both projects. As built (ticket 02): `tools/browser-closure.ts` computes the list with the TypeScript compiler API, so it follows type-only imports as `tsc` does, which an esbuild metafile does not; that is why the first list is 75 of 134 files, not 79 of 132. `npx tsx tools/browser-closure.ts --write` regenerates `files` and `tools/browser-closure.allowlist.json`; `tools/browser-closure.test.ts` fails when either is out of date. `noUncheckedSideEffectImports` is on, so a bare `import "node:fs"` fails too. As built (ticket 21): the final form. `files` is `["src/browser/globals.d.ts", "src/browser.ts"]`, `moduleSuffixes` of `.browser` first makes `tsc` resolve `default-host.ts` to `default-host.browser.ts` as the bundle does, the allowlist and `--write` are gone (nothing is left to allow, 141 of 141 files are clean), and `tools/browser-closure.ts` only says which file broke the ratchet.
- **D8. Zip with `fflate`** (MIT, sync `unzipSync` and `zipSync`), not hand-rolled and not `CompressionStream`: zip edge cases (data descriptors, UTF-8 name flag, Windows backslashes, directory entries, `__MACOSX/` and `._*` junk that would otherwise be listed as `*.xml` packages) are a bug farm, and the VFS is sync. Pinned exact version. As built, the adapter uses only `fflate`'s `inflateSync` and `deflateSync`, under a zip reader and writer of its own, because `unzipSync` and `zipSync` cannot meet HOST-250 and HOST-251 (the reasons are at the head of `src/browser/zip.ts`).
- **D9. Browser test path = vitest browser mode with the Playwright provider**, headless Chromium, Firefox and WebKit for everything on the in-memory path; the File System Access adapter is tested against OPFS handles (`navigator.storage.getDirectory()`, available in all three) so it needs no picker. A separate `npm run test:browser` and a separate CI job; `npm test` and the pinned `.no-mistakes.yaml` commands do not change (browser binaries are not a gate prerequisite). `chrome-devtools-axi` is for ad-hoc smoke and the reference page, not the suite.
- **D10. Browser tests read fixtures through vitest browser `commands` (Node-side file reads) or fetch from the dev server, a curated list of cases (about 6 MB), never a bundle of the 373 MB.** The assertion code is shared with the Node replay tests, not copied. As built (ticket 22): the set is 12.7 MB (12 718 696 bytes; `src/browser/fixture-set.ts`), with the shared 2.7 MB PackageDefinition blob read from one file. Two more copies of that list cannot go, and they are most of the excess: the language-resource export that ticket 24 requires (every such 14.35 case has a list of its own, 2.7 MB) and a 14.0.7 language pack that ticket 25 requires (each holds the list inside its transcript, 2.8 MB). Without them the set is 7.2 MB. One exception to sharing (HOST-264): `src/browser/engine-compat.browser.test.ts` keeps its own copy of the tree `dump` of `src/xml/vectors.test.ts`, because that test stays unedited.
- **D11. Heavy work belongs in a Web Worker** (sync XML, sync VFS, a 14.35 export with many items). The core is main-thread-agnostic; the Worker wrapper is its own ticket.
- **D12. Browser deviations are host rules, not engine bugs.** They go in `spec/browser-host.md` as `HOST-2xx` (block below) and not in `spec/bugs.md`, which registers engine bugs. Known ones: `fetch` cannot tell refused from unresolved from a TLS failure, so the browser transport reports one class ("Unable to connect to the remote server"); `Host`, `Cookie` and `Content-Length` are forbidden request headers and are dropped by the transport while the recorded request stays unchanged; `Set-Cookie` is invisible, so the cookie jar is inert and the browser's own jar is used; `statusText` is empty over HTTP/2, so the reason phrase is filled from the standard table (the `(500) Internal Server Error` text in `connection.ts`); a redirect is followed (a manual redirect is opaque in browsers).
- **D13. Rule ids.** The spec coverage test fails on a rule that is defined but cited nowhere, so each ticket adds its rules in the same PR as the code that cites them. Block `HOST-200` to `HOST-299` (document `spec/browser-host.md`): 200s seam and environment, 210s file system, 230s transport, 240s digest, clock and time zone, 250s adapters, 260s bundle and entry, 270s facade and Worker. No new prefix, so `spec/coverage.ts` needs no change.
- **D14. Differential first.** Wherever a Node implementation is replaced by a portable one (path, digests, VFS, Buffer), the ticket adds a differential or conformance test against the Node original before anything depends on it. The browser parity claim then rests on tests that fail in Node CI, not only in a browser.

## The one POC, and why

Whether a real Aras server (12 SP9, R23, R35) answers a cross-origin browser request cannot be settled by reading code: the `OPTIONS` preflight for the custom headers the client sends (`LOCALE`, `TIMEZONE_NAME`, `SOAPAction`, `AUTHUSER`, `AUTHPASSWORD`, `DATABASE`, `Authorization`, `X-Aras-Authorization`, `Aras-Request-ReadOnly`), the OAuth discovery and token endpoints, `Access-Control-Allow-Credentials` for the `ASP.NET_SessionId` cookie the engine replays today (`spec/wire.md`), and the exposed response headers. If the servers do not allow it and cannot be configured, the browser can only work same-origin or behind a proxy, which changes the product answer to Q1 and the design of the fetch transport. Nothing else is a POC: the VFS, path, digest and Buffer work are fully specifiable from the existing code and fixtures.

The POC's results are recorded in [`browser-cors-poc.md`](browser-cors-poc.md).

## Standing acceptance of every ticket

1. One PR through the no-mistakes pipeline. `npm run typecheck && npm test` pass; no assertion, case or fixture of an existing test changes to make it pass. The only edit an existing test file may take is an import line when a symbol moves.
2. The recorded-fixture replays (`run-replay*.test.ts`, `import-run.replay.test.ts`, `transcripts.test.ts`, wire captures) are byte-identical before and after.
3. Spec first: the `HOST-2xx` rules of the ticket are written in `spec/browser-host.md` and cited with `@spec`; a moved or new symbol is updated in `spec/source-map.json` in the same PR; no decompiled code is committed.
4. Browser-reachable code is added to the `tsconfig.browser.json` file list in the ticket that makes it clean (D7).
5. Live Aras only through arashouse leases per AGENTS.md "Live Aras"; scratch-only names; leases returned.

The CLI (`src/cli/**`, its `node:fs` use and `membership-server.ts`'s `node:crypto`), `oracle/`, `tools/` and the fixtures tooling stay Node-only. No change to engine behaviour, the spec's engine rules, or `COMPLETE_ENGINES`.
