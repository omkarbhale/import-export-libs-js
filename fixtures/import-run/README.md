# Import orchestration and registration: probe evidence

Recorded on Windows PowerShell 5.1 (.NET Framework 4.8), NTFS, on 2026-10-19. It backs `spec/import-run.md` (`IMP-400` to `IMP-499`) for 14.0.7, and, for 14.35, the `[14.35]` variants of the import documents (`spec/import-load.md`, `import-checks.md`, `import-delayed.md`, `import-merge.md` and `import-run.md`). Nothing here is Aras code or a credential, and no server was contacted.

| File | What |
|---|---|
| `probe-14.0.7.txt` | The real 14.0.7 engine (vendored `oracle/native/14.0.7/Libs.dll` and `IOM.dll`, staged to `%LOCALAPPDATA%`) run through `ImportExportManager.ImportSolutions`, `PackageDefinitionManager` and the `CItemHelper` methods the import uses. One `=== name` section per scenario. A scenario that runs `ImportSolutions` lists the result or the exception, every request IOM was handed (`REQUESTS`, numbered, CR and LF escaped as `\r` and `\n`), every message (`channel \| text`), the console text, and the log file (`LOG`). The date-time of the log is replaced by `<DATETIME>`, the run folder by `<ROOT>` and the identity of the machine's user by `<WINUSER>`. A scenario that calls a method directly lists each call with its result or exception and the requests it made. |
| `probe-14.35.txt` | The same scenarios, `s01` to `s64`, run against the real 14.35 engine (vendored `oracle/native/14.35/Libs.dll`, `IOM.dll` 15 and its dependencies), plus the scenarios `n01` to `n09` that exist to expose a 14.35 change. The `s` sections give the same requests, messages, console and log as 14.0.7 except where the 14.35 rules say they differ (the cancel scenarios `s09`, `s09b`; the error-block texts; `Adding PackageDefinition for`; `os_user`; the `Server error` text of `WIRE-051`). The identity of the machine's user is replaced by `<USERNAME>` (14.35 writes the bare user name) and `<WINUSER>` (14.0.7 wrote `DOMAIN\user`). |
| `probe-12.0.txt` | The `s` scenarios through the vendored 12.0 `Libs.dll` and `IOM.dll`, for the `[12.0]` variants of `spec/import-run.md` (`probe/run.sh <repo> <out> 's*' 12.0`). Its `REQUESTS` equal the 14.0.7 file's scenario by scenario, apart from `s37-not-logged-in` (12.0 needs no login) and `s64-discussion-template` (the nested actions differ); the messages, console and log differ as the 12.0 rules say. A date cut by the 12.0 log truncation (spec `IMP-412`) is shown as `<DATETIME, cut>`. `s64-discussion-template` is new and is in all three files. |
| `probe/` | The PowerShell and C# that recorded it. `probe.ps1` builds package folders, a manifest and a log under a work folder, and answers the engine's requests from a small model of the server (`Model-Respond`); `Probe.cs` is the stub connection and the recording message factory. `run.sh <repo> <out> [scenario glob] [engine]` stages the toolset of `engine` (`14.0.7`, the default, or `14.35`) and the scripts to `%LOCALAPPDATA%\libsjs-22-probe`, runs them and removes the staging folder. The glob matches scenario names (`n*`, `s09*`). |

**The server is a model.** The stub answers `get` with "no items" unless a scenario says otherwise, answers `add` with an id derived from the name, and never evaluates the engine's AML. So the files show exactly what the engine sends and how it reacts to the answers the scenarios script; they do not show what Aras answers. The import fixtures of wayfinder ticket 25 record that.

The `n` scenarios (ticket 53) are also in `probe-14.0.7.txt`, so each can be read against both engines: `n01` repeated lookups (cache hits), `n02` a failing lookup (the log line), `n03` a type definition that is stale at first, `n04` a `DiscussionTemplate` relationship in two items, `n05` identical delayed entries and a Property addressed by `where`, `n06` a versionable root whose `related_id` holds an `Item` with no id, `n07` the size of the log file during a run, `n08` a cancel during the delayed resolution, `n09` what a failed lookup leaves in the cache.

Line terminators in `probe-14.0.7.txt` and `probe-14.35.txt` are CRLF as the probe wrote them. `.gitattributes` keeps them.
