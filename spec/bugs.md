# Reproduced engine bugs

Every engine bug the library reproduces on purpose is registered here. The bug also has its own rule in the area document that defines its behaviour. Nothing is fixed silently.

Each entry follows this shape:

```markdown
## EXP-000: short name

- **Behaviour:** what the engine observably does.
- **Why it is a bug:** what a correct engine would do instead.
- **C# location:** `Namespace.Type::Member` (look it up in `spec/source-map.json` for the lock).
- **Versions:** 12.0, 14.0.7, 14.35 (whichever are affected).
```

The coverage test checks that every heading here names a rule defined in an area document.

## WIRE-024: the version refusal has faultcode 0 and names no versions

- **Behaviour:** when the server's major version is outside the engine's window, `CItemHelper.Login()` throws with faultcode `0`, and its text reads `You are trying to use incompatible utility of version Aras.Tools.SolutionUpgrade.ArasVersion with innovator version Aras.Tools.SolutionUpgrade.ArasVersion.`
- **Why it is a bug:** faultcode `0` means "no items found" everywhere else in the engine, so the refusal can be taken for an empty result. The version type has no text form, so neither version reaches the message.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::Login`.
- **Versions:** 12.0, 14.0.7.

## WIRE-054: the version probe crashes when only one of VersionMajor and VersionMinor exists

- **Behaviour:** when the first probe request returns exactly one Variable, the probe throws `System.IndexOutOfRangeException`, even for the Variable that exists, and the error escapes login.
- **Why it is a bug:** the engine looks the Variables up from the envelope down, but IOM has narrowed a single-item result to that item. A correct engine would read the Variable that exists and report the missing one.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::GetInnovatorServerVersion`.
- **Versions:** 12.0, 14.0.7.

## WIRE-055: non-ASCII password characters hash as `?`

- **Behaviour:** IOM hashes the ASCII bytes of the password, so each non-ASCII character becomes `?` before the MD5 or SHA-256 digest is taken.
- **Why it is a bug:** the server receives the digest of a different password, and passwords that differ only in non-ASCII characters are interchangeable. A correct client would hash the UTF-8 bytes.
- **C# location:** IOM's password hashing, reached from `Aras.Tools.SolutionUpgrade.CItemHelper::Login`.
- **Versions:** 12.0, 14.0.7.

## EXP-104: the ItemType auto-generated relationship removal acts on a copy

- **Behaviour:** after removing the Client Event `cmf_OnShowContainer` from the real response, the engine copies the response, looks up the `cmf_ContentType` items linked to the ItemType, and removes the relationships of their generated types from the copy. The copy is discarded, so only the Client Event removal reaches the file. The lookup still costs one `ApplyAML` request per ItemType export, and can fail: `Not a single item` when several content types are linked, an `ArgumentException` when a generated type has no single matching relationship.
- **Why it is a bug:** the removals exist to keep auto-generated relationships out of the exported ItemType, and they edit a document nobody writes.
- **C# location:** `Aras.Tools.SolutionUpgrade.CExportItems::RemoveAutoGeneratedRelationships`.
- **Versions:** 12.0, 14.0.7.

## EXP-112: the Form field catch handles the wrong fault

- **Behaviour:** when the Property fetch for a Field's `propertytype_id` fails with faultcode `0` (not found), the engine sets a "Unable to get property" detail and rethrows, aborting the form. Any other fault is swallowed and the `propertytype_id` stays a plain id. The message reads the `type` attribute but is guarded by `keyed_name`, so `keyed_name` without `type` raises a `NullReferenceException` inside the catch.
- **Why it is a bug:** the handling is inverted: a missing Property is the case that could be skipped, and the real failures are the ones that are hidden.
- **C# location:** `Aras.Tools.SolutionUpgrade.CExportItems::ProcessForm`.
- **Versions:** 12.0, 14.0.7.

## EXP-115: nodes already detached are still processed

- **Behaviour:** `processIndependentRelatedItems` selects all related items first and removes collapsed ones while it loops, so related items nested inside a collapsed item are still processed: their metadata lookups are sent and can fail, and their rewrite lands in a detached subtree.
- **Why it is a bug:** the requests and failures concern nodes that are no longer part of the output.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::processIndependentRelatedItems`.
- **Versions:** 12.0, 14.0.7.

## EXP-118: ac_PolicyAccessItemAttribute repeats the dr_RelationshipFamily routine

- **Behaviour:** the export calls the `dr_RelationshipFamily` routine (embedding `dr_Relationship` items found through `dr_relationship_id`, and re-indenting their `implementation_query`) a second time, unchanged, for `ac_PolicyAccessItemAttribute`.
- **Why it is a bug:** the second call is a copy of the first. A routine written for the `ac_` shape would not search for `dr_relationship_id` or re-indent an `implementation_query`.
- **C# location:** `Aras.Tools.SolutionUpgrade.CExportItems::Export` (the call) and `::IncludeDrRelationshipAsValue`.
- **Versions:** 14.0.7.

## EXP-270: a `]]>` in a FileSelectorTemplate reference fails the whole item

- **Behaviour:** the transform writes a FileSelectorTemplate's `reference` raw between `<![CDATA[` and `]]>`. A value that contains `]]>` ends the CDATA early, the output is malformed, the reload throws `XmlException` (`']]>' is not allowed in character data.`), and the item fails with that message followed by ` Can't export item.`
- **Why it is a bug:** a correct engine would split the section (`]]]]><![CDATA[>`), as it does for the other CDATA elements, so the item exports.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::ApplyXsl` (the stylesheet it runs), failing at the reload that follows.
- **Versions:** 12.0, 14.0.7.

## EXP-271: identity and system-property tests are substring tests

- **Behaviour:** the system Identity test and the system property tests look `|name|` up inside one long `|`-delimited string, so a name that contains `|` can match as a run of entries. A `keyed_name` of `World|Creator` exports as a system Identity `get` named `World|Creator`, and a Field whose property is named `state|itemtype` is treated as a system property.
- **Why it is a bug:** a correct engine would compare against the entries one at a time.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::ApplyXsl` (the stylesheet it runs).
- **Versions:** 12.0, 14.0.7.

## EXP-272: a Method-valued property without a keyed name exports as a Method `get` with an empty name

- **Behaviour:** `method`, `pre_action`, `post_action`, `on_complete` and `content_generator` on their Items are rewritten from the element's `keyed_name` attribute. Without one, including a null element such as `<method is_null="1"/>`, the output is a `get` of a Method with an empty `name`.
- **Why it is a bug:** the reference cannot be resolved on import, and a null property should stay null or be left out.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::ApplyXsl` (the stylesheet it runs).
- **Versions:** 12.0, 14.0.7 (14.35's `is_null` drop template changes this).

## EXP-540: packages exported in the referenced pass are missing from the manifest

- **Behaviour:** the referenced-items pass exports each referenced package into its own directory and log section, but `imports.mf` has no `package` entry for it, only the `dependson` entries under the main package.
- **Why it is a bug:** an import from the manifest skips packages the export produced, because the manifest lists a dependency but not the package that holds its items.
- **C# location:** `Aras.Tools.SolutionUpgrade.ImportExportManager::ExportReferencedElements`.
- **Versions:** 12.0, 14.0.7.

## EXP-541: a package-definition query that fails inside an export crashes on the log file

- **Behaviour:** `GetSolutions2Xml` opens a second writer on the log file to record its error while `ExportSolutions` still holds the file, so the open fails with an `IOException` that escapes `ExportSolutions` before its `try` block. No manifest is saved.
- **Why it is a bug:** the real error (the failed query) is replaced by a file-sharing error, and the run leaves no manifest.
- **C# location:** `Aras.Tools.SolutionUpgrade.ImportExportManager::GetSolutions2Xml`.
- **Versions:** 14.0.7.

## EXP-542: a missing package definition aborts the whole export

- **Behaviour:** a `CItemException` from the package-definition lookup, the dependency query or a referenced element without id or type is not a `SystemException`, so it escapes `ExportSolutions` after the manifest is saved. Later packages and the referenced pass never run, and no warning is sent.
- **Why it is a bug:** the top-level handler reports other failures as a warning and ends cleanly, but these escape it, and one bad package stops every package after it.
- **C# location:** `Aras.Tools.SolutionUpgrade.PackageDefinitionManager::InitSolution`, `Aras.Tools.SolutionUpgrade.PackageDefinitionManager::FindReferencedElements`, `Aras.Tools.SolutionUpgrade.ImportExportManager::ExportSolutions`.
- **Versions:** 12.0, 14.0.7.

## EXP-543: a cancel during the main loop still runs the referenced pass

- **Behaviour:** after a cancel, the referenced pass still wipes and recreates the first referenced package's directory, sends its `currentPackage` message and writes its log header, and the cancel is noticed only at that package's first item.
- **Why it is a bug:** a cancelled export should stop. The wipe can delete a finished main package's output when the dependency shares its directory.
- **C# location:** `Aras.Tools.SolutionUpgrade.ImportExportManager::ExportSolutions`, `Aras.Tools.SolutionUpgrade.ImportExportManager::ExportReferencedElements`.
- **Versions:** 12.0, 14.0.7.

## EXP-544: package and dependency names are interpolated unescaped into XPath and AML

- **Behaviour:** a package or dependency name with an apostrophe makes the manifest or dependency XPath malformed, and the run ends with the XPath error as a warning (`'imports/package[@name='X'Y']' has an invalid token.`). A name that closes the literal and adds a predicate selects other nodes.
- **Why it is a bug:** a legal package name cannot be exported, and a crafted one changes which nodes the engine reads.
- **C# location:** `Aras.Tools.SolutionUpgrade.ImportExportManager::ExportSolutions`, `Aras.Tools.SolutionUpgrade.ManifestFile::AddPackage`, `Aras.Tools.SolutionUpgrade.ManifestFile::AddDependsOn`, `Aras.Tools.SolutionUpgrade.ManifestFile::AddReferencedElement`.
- **Versions:** 12.0, 14.0.7.

## IMP-006: a leading backslash is trimmed from every path, so UNC package folders fail

- **Behaviour:** `IOWrapper.NormalizeLongPath` strips every leading `\` and `?` from a path before using it, so `\\server\share\pkg` becomes the relative path `server\share\pkg` and the import fails with `DirectoryNotFoundException` against the current directory.
- **Why it is a bug:** the code means to remove the `\\?\` long-path prefix, but `TrimStart` takes a character set. A correct engine would remove the prefix only.
- **C# location:** `Aras.Tools.SolutionUpgrade.IOWrapper::NormalizeLongPath`.
- **Versions:** 14.0.7.

## IMP-012: the transform failure message names export.xsl when build.xsl ran

- **Behaviour:** an error while applying any stylesheet, including `build.xsl`, is reported with the text ` Error of  applying export.xsl.` (two spaces after `of`).
- **Why it is a bug:** the message names the wrong stylesheet and is misspelled.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::ApplyXsl`.
- **Versions:** 14.0.7.

## IMP-013: the SOAP-ENV namespace replace also deletes the text from element content

- **Why it is a bug:** only namespace declarations should be removed. A script or comment holding that text is altered silently.

## IMP-022: a type counts as listed when `|type|` is a substring of the list

- **Behaviour:** `build.xsl` tests a type against its lists with `contains`, so `List|Sequence` is taken for a listed type and dropped, where an unlisted type of that spelling would be imported.
- **Why it is a bug:** a type name should be compared with each name of the list, not searched for in the joined text.
- **C# location:** the embedded stylesheet `build.xsl`, applied by `Aras.Tools.SolutionUpgrade.ImportExportManager::LoadPackageDom` through `CItemHelper::ApplyXsl`.
- **Versions:** 14.0.7.

## IMP-026: an ItemType edit or delete is copied once for every earlier ItemType or RelationshipType add

- **Behaviour:** after each `ItemType` or `RelationshipType` add, the stylesheet copies every later `ItemType` sibling that has an action other than `add`. A later `edit` or `delete` therefore appears once per earlier add, and the engine imports each copy. The same happens to nested items inside `Relationships`.
- **Why it is a bug:** the sibling should be written once. Repeated `edit` items waste requests, and a repeated `delete` after the first has run can fail.
- **C# location:** the embedded stylesheet `build.xsl`, applied by `LoadPackageDom` through `ApplyXsl`.
- **Versions:** 14.0.7.

## IMP-029: build.xsl silently drops items whose type is listed but whose action is not selected

- **Behaviour:** an item of a listed type whose action no group takes, such as a `delete` or `merge` of a `List` or `Method`, an `ItemType` with no action, or an `ItemType` `delete` with no earlier add, is not written to the ordered output. Nothing is logged and the import reports success.
- **Why it is a bug:** package content is lost without a message. A correct engine would import the item or refuse the package.
- **C# location:** the embedded stylesheet `build.xsl`, applied by `LoadPackageDom` through `ApplyXsl`.
- **Versions:** 14.0.7.

## EXP-032: the "Unable to get definition" text names `System.Xml.XmlAttribute`

- **Behaviour:** when a metadata lookup (the is_versionable lookup of an ItemType, and the related-item metadata lookups) fails with faultcode 0, the engine rewrites the fault's detail to `Unable to get definition of System.Xml.XmlAttribute: {name}`.
- **Why it is a bug:** the text is meant to name the type that was asked for. The engine formats the `type` attribute node with `ToString()`, which is the .NET type name, not the attribute's value.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::GetTypeAmlInner`.
- **Versions:** 12.0, 14.0.7.

## EXP-047: a failed poly-type lookup is remembered as "no poly-types"

- **Behaviour:** the list of polymorphic ItemType names is created before its request is sent. When the request fails with a faultcode other than 0, the first caller gets the error, but every later call of that `CItemHelper` finds the empty list, returns it, and sends nothing. Items exported after the failed one keep their `data_source` references to polymorphic types unrewritten, with no error.
- **Why it is a bug:** a failed lookup should not be taken for an answer. A correct engine would leave the list unset, so the next call asks again.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::GetPolytypeNames`.
- **Versions:** 12.0, 14.0.7.

## EXP-055: stack text in `faultstring` is not reproduced (deviation)

- **Behaviour:** where the engine builds a `CItemException` from a caught exception, it puts the exception's stack trace in `faultstring`. The trace is a list of .NET frames, framework internals included, so it differs between .NET Framework builds and is not stable even across the engine's own runs on different machines. The library writes the exception's type name, a colon, a space and its message there instead, with no frames.
- **Why it is a bug:** this is a deviation, not an engine bug. The frames cannot be reproduced, so a log or message that quotes such a `faultstring` differs from the engine's on that one field, and parity checks compare it masked.
- **C# location:** `Aras.Tools.SolutionUpgrade.CExportItems::Export`, `CItemHelper::GetCurrentIdOfVersion`, `CItemHelper::GetCustomFloatPropertiesOfTypeItem`, `PackageDefinitionManager::InitSolution` and `PackageDefinitionManager::FindReferencedElements`.
- **Versions:** 12.0, 14.0.7, 14.35.

## EXP-402: the SOAP-ENV namespace strip deletes that text from element content

- **Behaviour:** after the transform, `ApplyXsl` removes every occurrence of `xmlns:SOAP-ENV="http://schemas.xmlsoap.org/soap/envelope/"` from the serialized output, so the same text is also removed from element text and CDATA: a method whose code contains it exports without it, and a `comments` element holding only that text exports as `<comments></comments>`.
- **Why it is a bug:** the strip is meant to drop the namespace declaration the transform copies onto each `Item`. A correct engine would remove the declaration nodes, not text.
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::ApplyXsl`.
- **Versions:** 12.0, 14.0.7.

## EXP-404: a type with incomplete default permission data fails the item with a NullReferenceException

- **Behaviour:** when the ItemType answer lacks `is_relationship` or `use_src_access`, or neither of them is `1` and the type has no default Allowed Permission, the item fails with `Object reference not set to an instance of an object. Can't export item.`
- **Why it is a bug:** a missing default permission is a normal state (it means the permission is kept), and a missing flag could be read as `0`. A correct engine would keep the `permission_id` instead of failing the export of the item.
- **C# location:** `Aras.Tools.SolutionUpgrade.CExportItems::RemovePermissionIdWhenItMatchesToDefaultPermission`.
- **Versions:** 12.0, 14.0.7.

## EXP-406: CdataFilterXml decodes entity-like text inside CDATA and fails on a bare ampersand

- **Behaviour:** the step sets the element's markup to the HTML-decoded markup, so text inside a CDATA section is decoded too (`&amp;nbsp;` becomes `&nbsp;`, `&lt;b&gt;` becomes `<b>`), and plain text holding `&amp;` becomes a bare `&` that cannot be loaded, which fails the item.
- **Why it is a bug:** CDATA content is literal text and must come out as it went in, and a decoded document must still be well formed.
- **C# location:** `Aras.Tools.SolutionUpgrade.CExportItems::CdataFilterXml` (12.0: `CdataFilterXmlInMacCondition`, for `mp_MacPolicy` only).
- **Versions:** 12.0, 14.0.7.

## EXP-411: RemoveNamespaceNodes tests for a null prefix that never occurs

- **Behaviour:** the condition "prefix is null or prefix is not empty" can only act through its second half, because .NET reports the prefix of an unprefixed attribute as the empty string. Only prefixed attributes of non-namespaced `Item` elements are removed.
- **Why it is a bug:** the first half is dead code, written for a null that never happens. Its intent cannot be told from the code; the library reproduces the effect (prefixed attributes go, plain attributes and `xmlns=""` stay).
- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::RemoveNamespaceNodes`.
- **Versions:** 12.0, 14.0.7.

## EXP-416: packages with the same last segment wipe each other's output folder

- **Behaviour:** a non-standard package is exported into `<last segment>\Import`, and the folder is deleted recursively and recreated before each package. Two packages with the same last segment, and a referenced package whose last segment equals a main package's, delete each other's files; packages with an empty last segment (a trailing dot) share `Import`.
- **Why it is a bug:** an export deletes the output of another package of the same run, without a warning, and the manifest still lists it.
- **C# location:** `Aras.Tools.SolutionUpgrade.ImportExportManager::CreateOutputDir`.

## EXP-419: two items with the same file name overwrite each other

- **Behaviour:** the file name is the keyed name (case-insensitively on Windows), nothing checks for an existing file, and the export reports every item as successful. Only the last item of a name keeps its file.
- **Why it is a bug:** items are lost from the exported package silently. A correct engine would detect the collision, or name the file by id.
- **C# location:** `Aras.Tools.SolutionUpgrade.CExportItems::Export`, writing through `Aras.Tools.SolutionUpgrade.IOWrapper::XmlDocumentSaveWithSettings`.

## EXP-422: NormalizeLongPath turns a UNC path into a relative path

- **Behaviour:** `NormalizeLongPath` removes all leading `\` and `?` characters, so `\\server\share\dir` becomes `server\share\dir` and is then resolved against the process's current directory. A working directory, manifest or log given as a UNC path is read from or written to the wrong place or fails.
- **Why it is a bug:** the trim is meant to drop a `\\?\` prefix. A correct engine would remove only that prefix. The same code returns the trimmed path, not the full path, when it is shorter than 255 characters.
- **C# location:** `Aras.Tools.SolutionUpgrade.IOWrapper::NormalizeLongPath`.
- **Versions:** 14.0.7.

## EXP-428: a failed write leaves a partial item file

- **Why it is a bug:** a truncated file looks like an export result. A correct engine would serialize before writing, or delete the file on failure.
- **C# location:** `Aras.Tools.SolutionUpgrade.IOWrapper::XmlDocumentSaveWithSettings`.
- **Versions:** 12.0, 14.0.7.

A later relationship element with the same `id` in the run is left as it is and is not queued.

## IMP-180: the detail texts the checks attach to a fault never reach the error

- **Behaviour:** the type-definition lookup and the RelationshipType and grid checks set `faultdetail` on a not-found fault, but `RecurseCheck` builds its error from the exception's `Message`, which does not change, so the intended texts (`Bad Grid …`, `Bad RelationshipType …`) are never shown. The type-definition text also names `System.Xml.XmlAttribute` instead of the type.

## MAN-005: a path that starts with a backslash loses it

- **Behaviour:** `IOWrapper.NormalizeLongPath` removes every leading `\` and `?` from a path before using it. A UNC path `\\host\share\imports.mf` is then read or written as the relative path `host\share\imports.mf`, and `\Users\me\imports.mf` as `Users\me\imports.mf`. The same applies to the folder of a package whose manifest path is UNC or starts with `\`.
- **Why it is a bug:** the code means to strip the `\\?\` long-path prefix, but it passes the prefix's characters as a set, so it also strips the root of any UNC or drive-less path.
- **C# location:** `Aras.Tools.SolutionUpgrade.IOWrapper::NormalizeLongPath`.
- **Versions:** 14.0.7.

## MAN-011: a package name ending in `.` or empty gets the path `\Import`

- **Behaviour:** `ManifestFile.AddPackage` derives the path of a non-standard package from the text after the last `.`. For `trailing.`, `a.b.` or an empty name that text is empty, and the path is written as `\Import`.
- **Why it is a bug:** import resolves `\Import` as a rooted path, so the package's folder is looked up away from the manifest. A correct engine would use the name or refuse it.
- **C# location:** `Aras.Tools.SolutionUpgrade.ManifestFile::AddPackage`.
- **Versions:** 12.0, 14.0.7.

## MAN-014: names are put into XPath unescaped

- **Behaviour:** the manifest lookups and the database test of the ordering build their XPath from the name with `string.Format`. A name with `'` makes the expression invalid and throws `XPathException`; a name that is valid XPath (`x' or @name='My.Pkg`) matches other nodes, so `AddPackage` returns an existing package and adds nothing.
- **Why it is a bug:** names are data, not expressions. A correct engine would compare the attribute value or escape the quote.
- **C# location:** `Aras.Tools.SolutionUpgrade.ManifestFile::AddPackage`, `AddDependsOn`, `AddReferencedElement`, `GetPackageNode`, `GetDependsOn`, `MoveToOrderedList`.
- **Versions:** 12.0, 14.0.7.

## IMP-016: a DOCTYPE with an internal subset or an external identifier is not loaded

- **Behaviour:** .NET's `XmlDocument.LoadXml` loads any DOCTYPE: it declares the entities and attribute defaults of an internal subset and reads the file named by `SYSTEM` or `PUBLIC`. The port loads only a DOCTYPE with a name (`<!DOCTYPE a>`, `<!DOCTYPE a[]>`) and throws `NotSupportedException` for any other.
- **Why it is a bug:** this is a deliberate deviation of the library, not an engine bug. Modelling DTD declarations would add entity expansion and default attributes to the DOM for a case no real package or manifest has: a package file with a DOCTYPE fails the import in the engine anyway (IMP-010).
- **C# location:** `System.Xml.XmlDocument` (the .NET Framework), reached from `Aras.Tools.SolutionUpgrade.IOWrapper::XmlDocumentLoad`.
- **Versions:** 14.0.7.

## MAN-018: Hashtable order becomes random after 100 probe collisions

- **Behaviour:** .NET Framework switches a `Hashtable` to a per-process randomized string hash when one insertion walks more than 100 occupied buckets, so the enumeration order differs from run to run. The port cannot follow a random order and throws an error naming the table and key at that point.
- **Why it is a bug:** an engine's output order should not depend on the process. This is a deliberate deviation of the library, unreachable with real keys.
- **C# location:** `System.Collections.Hashtable` (the .NET Framework), reached from `Aras.Tools.SolutionUpgrade.ManifestFile::GetDependsOnInfo` and every other table the engine builds.
- **Versions:** 12.0, 14.0.7.

## MAN-024: a package named twice in the import list fails the whole import

- **Behaviour:** `GetPackageNamesInImportOrder` copies the requested names into an `OrderedDictionary` with `Add`, so a name that occurs twice throws `System.ArgumentException` (`Item has already been added. Key in dictionary: 'A'  Key being added: 'A'`) and no package is imported.
- **Why it is a bug:** importing a package once is the obvious meaning of a repeated name.
- **C# location:** `Aras.Tools.SolutionUpgrade.ManifestFile::GetPackageNamesInImportOrder`.
- **Versions:** 12.0, 14.0.7.

## MAN-025: a dependency cycle that avoids the starting package kills the process

- **Behaviour:** `MoveToOrderedList` recurses without bound when a pending package is in a cycle that does not contain the package being placed (`A>B`, `B>A`, `C>A`, importing `C,A,B`; or `A>B`, `B>B`). The process ends with a stack overflow: `Process is terminated due to StackOverflowException.` The port stops with an error of that text at a nesting depth of 100,000, so it fails catchably where the engine dies.
- **Why it is a bug:** a cyclic manifest should give the circular-dependency warning, not end the process. This is the one deviation that cannot be avoided (round 5, line 9).
- **C# location:** `Aras.Tools.SolutionUpgrade.ManifestFile::MoveToOrderedList`.
- **Versions:** 12.0, 14.0.7.

## EXP-615: removing references while walking the node list skips and revisits nodes

- **Behaviour:** the unknown-package removal visits `SelectNodes` results with `foreach` and removes nodes from the document as it goes. .NET Framework builds that list lazily, one element ahead, from iterators over the live tree, so the loop still visits nodes inside a subtree it has just detached, records references from them, and never visits matches that come after a detached subtree. Those references stay in the exported file. Example: removing `a` from `a(a1, a2), b, c(c1)` visits `a, a1, a2, b, c` and not `c1`.

- **C# location:** `Aras.Tools.SolutionUpgrade.CItemHelper::RemoveReferencesToAnotherPackages`.
- **Versions:** 12.0, 14.0.7.
